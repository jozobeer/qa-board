# 勉強会ごとのQ&Aボード

ボードの名前を入力して作ると共有URLが発行され、そのURLを開いた参加者だけが同じボードに質問と回答を書けるようにする。

## 意図

勉強会やイベントの主催者が、その回の参加者から匿名で質問を集めたい場面で使う。

今のボードは全世界にひとつしかなく、別のイベントの質問が同じ一覧に並ぶ。自分の回の質問だけを追えないと、回答する側も参加者も使えない。ボードごとに分け、共有URLを知る人だけが同じボードを見る形にする。

## 受け入れ条件の種

- ルートを開くとボード名の入力フォームだけが表示され、質問一覧と投稿欄は表示されない
- ボード名を入力して作成すると共有URLに遷移し、その共有URLを画面上でコピーできる
- 共有URLを別ブラウザ（別セッション）で開くと、同じボード名と同じ質問一覧が表示される
- 別々に作成した2つのボードは互いに影響せず、片方の質問や回答が他方に現れない
- 存在しないIDの共有URLを開くと、見つからない旨が表示され投稿欄は出ない
- 片方のボードの質問IDを使っても、もう片方のボードのURLからその質問へ回答できない

## 実装メモ

同じ形の改修を checkin-counter（KV）で先に済ませてある。URL形状とIDの扱いはそちらに揃える。

- 共有URLは `#/r/<id>` のハッシュ形式にする。実パスにすると存在しないアセットを index.html へ返すフォールバック設定が要り wrangler.jsonc に手が入る
- IDは `crypto.randomUUID().slice(0, 8)`。採番時に既存と衝突したら数回まで振り直す
- IDの形式を正規表現（`/^[0-9a-f]{8}$/`）で検証し、不正なら永続層を引く前に404を返す
- ルームの作成にも入力サイズ上限・名前の長さ上限・レートリミットを付ける。既存の書込レートリミットとは別のキー名前空間で数える
- `/api/health` の挙動は変えない。kojo の機械検証が依存している
- 受け入れ条件はひとつずつ Playwright テストに対応させる
- スキーマ変更は migrations/ に新しい連番のSQLファイルを追加して行う。適用済み migration の書き換えと app_meta テーブルの削除は禁止
- `questions` にボードを表す列を足す。`answers` は question_id 経由で従属するので列追加は要らない。ただし回答の書込みは、対象の質問がそのボードに属することを確かめてから受け付ける（列を足さないことと、所属を確かめないことは別）
- 既存のグローバルな質問は移行しない（本番の質問は0件）
